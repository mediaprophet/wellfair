## Architecture clarification (made this session)

**pair.html is the WebRTC bridge, not the vault.**

- The vault is the underlying WASM app (see `expert-authoring-tool/`, `user-runtime-lib/`)
- `pair.html` was built to extend the vault to desktop/laptop via WebRTC DataChannel
- The medication reminder/management UI was added to `pair.html` as a web-layer
  representation of vault data — this is temporary / demo scaffolding
- In production, the medication UI belongs in the vault app itself;
  `pair.html` should only handle signalling, consent, and serving sections

## Planned migration: pair.html → family of pages

The next session should restructure the web layer. Proposed layout:

```
docs/
  webconnect.html        ← rename/refactor of pair.html
                            ONLY: QR scan, profile selection, consent, serving
                            Remove: all vault business logic, medication UI, mock data

  vault.html (new)       ← standalone owner workspace (no desktop required)
                            PIN entry → medication reminders, notes, sanctuary
                            The "daily use" app: check meds, log entries, etc.
                            Reads/writes IDB directly
                            NOT dependent on any WebRTC session

  connector/index.html   ← unchanged (desktop side)

  demo/index.html (new)  ← demo landing page
                            Links to webconnect.html?demo and connector/?demo
                            Or auto-connects to vault demo account session
```

Key principle: **webconnect.html should have no vault business logic**.
It is a transport layer. All health data logic lives in vault.html (web layer)
or in the WASM vault app.

The `MedNotifier` abstraction, IDB stores, and all medication functions
should move from pair.html → vault.html in this migration.

## Known issues / tech debt

1. **`VAULT` not `VAULT_DATA`** — the mock data object in pair.html is `const VAULT`.
   Was briefly referenced as `VAULT_DATA` in new code — fixed. Watch for this.

2. **Activity log `permitted` arg** — `logActivity(msg, true)` is needed for
   owner-initiated actions. All medication log calls now pass `true`. Any new
   owner-side features must do the same.

3. **Demo mode `?demo` in connector** — `disconnect()` tries to navigate to
   `connector/` (relative URL) which may resolve incorrectly depending on server
   path. Verify with real deployment path.

4. **Wikidata SPARQL CORS** — queries go direct from browser to Wikidata.
   If COOP/COEP headers from `sw.js` cause issues, the Wikidata fetch will fail
   silently (the `catch` in `_lodFetchDetail` handles it). No crash, just no URI.

5. **RxNorm interaction API** — only fires when 2+ medications have saved `rxcui`
   values (i.e. were added via the LOD autocomplete). Mock meds have rxcui in
   the VAULT mock but IDB meds added manually won't until LOD lookup is used.

6. **Session TTL in demo mode** — `approveOwnerSession()` sets a 30-min TTL timer
   that calls `endSession()`. In demo mode this will kick the user out. Consider
   suppressing or extending TTL when `DEMO_MODE` is true.

## Watch-app connector (future)

The `MedNotifier` abstraction is the entry point:

```js
// Register a BLE watch handler:
MedNotifier.register(async (event) => {
  // event: { type: 'due'|'overdue', medication, scheduledTime, minutesLate }
  await bleWatch.sendNotification(event);
});

// Register a WebSocket handler for a companion web app:
MedNotifier.register(async (event) => {
  ws.send(JSON.stringify({ type: 'med_alert', ...event }));
});
```

The watch app connector would be a separate page/worker that:
1. Connects to a BLE peripheral (navigator.bluetooth) or WebSocket
2. Registers a MedNotifier handler
3. Optionally also reads the IDB schedule to push reminders proactively
